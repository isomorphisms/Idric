# Ordinary division with a negative operand

[Issue 149](https://github.com/isomorphisms/Idric/issues/149) sets the domain:
ordinary division with either operand negative enters complex arithmetic.
For exact integer inputs, −7 ÷ 3 represents −7/3 + 0i. A pair of negative
inputs still selects the complex domain even when the quotient is positive.
The issue leaves precision, result typing and explicit integer operations open.
The following candidate settles them only in an executable experiment.

## What the compiler does today

On the inspected compiler line at `b2f4c2488d0aa55cd947535eb9b61ff0e6bba963`,
the [Idriç lexer](../Parser/Lexer/Source.idr) maps ÷ to the existing / token.
The [prelude](../_/libs/prelude/Prelude/Num.idr) declares fractional division
with identical operand and result types. It supplies explicit integer
`div` and `mod` through a different interface. It supplies no
`Fractional Integer` instance. A signed-integer expression demanded to have an
integer result is therefore rejected. The existing [operator regression](../_/tests/idris2/basic/edric011/Main.idric)
uses an explicitly floating result. The [complex projective model](../COMPLEX-PROJECTIVE.md)
deliberately leaves its scalar carrier abstract. Its Gaussian-integer test
scalar cannot hold −7/3.

## Candidate type for exact integer inputs

Use one statically known outcome type for arbitrary pairs of signed integers.
A zero divisor returns a domain error. Otherwise, inspect both input signs
before normalizing the denominator. If either is negative, embed the exact
ratio in the complex field. If both are nonnegative, return a real exact ratio.
The two success alternatives have a common injection into the complex domain.
The public mathematical representation distinguishes the domains even when
both answers have the same coordinate value. A caller that needs this
distinction inspects the outcome. A caller requiring a complex value can embed
the real result. Complex-to-real narrowing requires an explicit operation.

A known sign allows a compiler to remove the corresponding test, provided the
observed result still agrees with the same operation on values read at runtime.
An ordinary conditional or function return thus keeps one static type across
both paths. A dependent result indexed by operand signs would allow stronger
static conclusions but force callers to carry signs across unrelated
branches. Unconditionally returning complex for positive inputs would alter
their established domain where a real division already exists. The explicit
choice lets us test these tradeoffs before making any language-wide change.

Use unbounded signed numerator and positive denominator for the first exact
slice. Several pairs can denote the same ratio, and cross multiplication with
unbounded integers determines equality. Reduction by a common divisor can be
deferred until a canonical byte format or an algorithm needs it. The imaginary
coordinate of a promoted exact quotient is zero by construction. A fixed
machine-width numerator or mandatory conversion through a float would lose
valid input values. Widen fixed-width signed inputs before taking their
magnitude, including the most negative value. This candidate specifies results
on exact integer operands only. The issue also motivates extending promotion to
real floating operands; handling their declared width, signed zeros, infinities
and unordered NaNs requires a separate contract. Never compare a complex
operand to zero to choose a sign branch.

## Explicit integer quotient and remainder

Keep `div` and `mod` available for callers explicitly requesting integral
outputs. For arbitrary-precision integers and a nonzero divisor, the current
Chez path is Euclidean: dividend = divisor × quotient + remainder and
0 ≤ remainder < |divisor|, for either divisor sign. The proposed ordinary
operator never invokes these as a substitute. A zero divisor remains outside
the explicit integer operations' specified domain. Preserve current explicit
operations on compatibility source. Changes to their convention, other
operators or inexact arithmetic require their own decisions.

## First compiler integration

1. Publish a shared exact integer ratio and explicit checked ordinary-division
   operation through the Idriç numeric layer. Define the result domain and its
   embeddings before choosing runtime layout. Use the [executable examples](../examples/autogenerated/signed-ordinary-division/attempt.md)
   to reject promotion by result sign, dropped denominator sign, integer
   truncation and narrowed arithmetic.
2. Add expected-type and overload tests before wiring notation. Test operands
   whose signed type is explicit, unannotated literals, typed floating and
   custom fractional consumers, `/` and `÷` within .idric, and .idr
   compatibility. A new `Fractional Integer` instance cannot express a wider
   codomain. Preserve both .idric spellings' equivalence on migrated operations
   and their original token spans if source-aware elaboration is needed.
   Include a dependent-use test that rejects an implicit conversion back to
   integer and one that explicitly embeds a successful result in the complex
   domain. Conditional consumers should compile against one stable type.
3. Carry the checked operation and result alternatives to direct DEX/ART,
   native ARM/Thumb and x86 as separate consumers. Exact integer component
   arithmetic must be supported or rejected at compile time. A host bignum,
   floating approximation, integer divide instruction or trap is insufficient
   as target acceptance. Before marking each target implemented, run genuine
   input/output cases for negative numerator, negative denominator, two
   negatives, zero dividend, zero divisor and a value beyond 64 bits. Check
   the outcome domain and exact coordinates, and distinguish compilation from
   target execution. Record missing primitive or representation support at the
   first failed case.

The executable two-step client now covers an already promoted quotient
divided by another exact integer. In (−7 ÷ −3) ÷ 5 the positive real
coordinate stays embedded in the complex domain and the result is 7/15 + 0i.
The same client accepts positive inputs and propagates a zero divisor from
either step. It imports the checked result type through a module interface.
General complex divisors and integration with the production operator remain
open.
